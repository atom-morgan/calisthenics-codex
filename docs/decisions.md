# Decisions

Short records of the choices that shaped this codebase: what we chose, why, and what we passed on. Newest at the bottom.

## 1. Supabase for auth and Postgres

**Decision:** Supabase provides both authentication and the database.

**Why:** `public.users.id` is the same UUID as `auth.users.id`, so there's no user sync between vendors, and a database trigger can create the profile row atomically at signup (see 5).

**Alternatives:** Clerk + Neon. Better prebuilt auth UI, but users would need to be synced into Postgres via webhooks: a second vendor and an eventual-consistency problem.

## 2. Drizzle over Prisma

**Decision:** Drizzle ORM with SQL migrations generated by drizzle-kit.

**Why:** The schema is plain TypeScript that maps closely to SQL, there's no generated client, and constraints that matter here (expression indexes, `CHECK`s) are declared in the schema itself. Generated migrations are plain SQL that can be reviewed and hand-edited when needed (see 9).

**Alternatives:** Prisma. More abstraction and tooling than this app needs.

## 3. Authorization lives in a server-side data access layer

**Decision:** Every read and write goes through functions in `src/server/` that take the user id from `requireUser()`, never from request input. Row Level Security is enabled on every table with **no policies**.

**Why:** The app connects to Postgres directly as the `postgres` role, which bypasses RLS, so RLS can't be the app's access control. Keeping the rules in TypeScript makes them easy to read and unit test. RLS-with-no-policies still matters: Supabase auto-exposes the `public` schema through a REST API reachable with the publishable key, and this closes that door entirely.

**Alternatives:** RLS policies as the primary authorization layer, querying through the Supabase client. Strong defense in depth, but the rules move into SQL policies that are harder to test and debug. A reasonable next step on top of the current design.

## 4. Proxy is an optimistic check only

**Decision:** `src/proxy.ts` refreshes the session and redirects signed-out users. Every page and Server Action still calls `requireUser()`.

**Why:** Proxy matches on URL paths, and Server Actions are POST endpoints, so a path-based check alone can be bypassed. Next.js recommends exactly this split: optimistic checks in Proxy, real checks next to the data.

## 5. Profile rows are created by a database trigger

**Decision:** An `AFTER INSERT` trigger on `auth.users` inserts the `public.users` row (`SECURITY DEFINER`, empty `search_path`, execute revoked from API roles).

**Why:** Signup and profile creation succeed or fail together. A user can't exist without a profile.

**Alternatives:** Insert the profile in the signup Server Action. Simpler to read, but a failure between the two writes leaves an auth user with no profile.

## 6. Mutations use Server Actions

**Decision:** Login, signup, logout, and workout creation are Server Actions. Auth forms post `FormData`; the workout form sends a typed object, validated with Zod as `unknown`.

**Why:** No hand-written API routes or client fetch code, and the Supabase client never ships to the browser. The workout form needs JavaScript for its dynamic rows anyway, so sending a typed object avoids parsing nested field names out of `FormData`.

**Alternatives:** Route Handlers plus client `fetch`. More code for the same result. Route Handlers remain the right tool for the Day 2 LLM endpoint if it streams.

## 7. Next.js Cache Components are off

**Decision:** `cacheComponents` and `partialPrefetching` (on by default in the Next 16 template) are disabled.

**Why:** Nearly every page is per-user, so there's little to cache, and per-user caching adds a class of bugs (serving one user's data to another). Pages that read the session render per request.

**Alternatives:** Keep them and use `<Suspense>` boundaries with `"use cache: private"`. Worth revisiting if public or shared pages appear.

## 8. Two database connection strings

**Decision:** The app uses Supabase's transaction pooler (`DATABASE_URL`, port 6543, `prepare: false`); migrations use the session pooler (`MIGRATION_DATABASE_URL`, port 5432).

**Why:** Serverless functions are short-lived and numerous, so they share pooled connections. The transaction pooler doesn't support prepared statements or the session-level behavior migrations rely on.

## 9. Ordering is stored explicitly and assigned by the server

**Decision:** `sets.exercise_position` records the order of exercises in a workout; `sets.set_number` orders sets within an exercise. Both are derived from array order in `createWorkout`, never accepted from the client.

**Why:** Without it the order a workout was performed in is lost (all sets in one save share `created_at`, since Postgres's `now()` is the transaction start time).

**Note:** The migration that added the column was hand-edited to add it as nullable, backfill, then set `NOT NULL`, since a `NOT NULL` column without a default can't be added to a table with rows. Applied migrations are never edited afterward.

## 10. Dates are calendar days

**Decision:** `workouts.performed_on` is a Postgres `date`, handled as a `YYYY-MM-DD` string and formatted in UTC. The form's default "today" is computed in the browser.

**Why:** A workout happens on a day, not at an instant. Parsing `"2026-11-04"` with `new Date()` gives midnight UTC, which displays as Nov 3 in US timezones. The server (UTC on Vercel) can't know the user's local date, so the form gets it from the browser via `useSyncExternalStore`, which avoids a hydration mismatch.

## 11. Natural-language entry fills the form; the form is the preview

**Decision:** Parsed text is added to the existing workout form, which the user reviews, edits, and saves through the same `createWorkout` path as manual entry. The parser runs in a Server Action (`parseWorkoutAction`) and never writes to the database.

**Why:** One save path and one set of validation rules. Editing a parsed result is just editing the form. Anything the parser couldn't read becomes a warning in the preview rather than a guessed value.

**Alternatives:** A separate read-only preview with Confirm/Edit steps: a second view of the same data and a second save path. A Route Handler (`POST /api/parse`) instead of a Server Action: worth it only if something other than our own UI needed to call it.

## 12. LLM output is never trusted

**Decision:** Three layers between the model and the database:

1. Structured output with a deliberately loose schema (shape only; exercise names constrained to an enum of the catalog).
2. `interpretModelOutput` validates every set with the form's own `setInputSchema`, drops bad ones with a warning, and maps names to ids.
3. The saved workout is validated again by `workoutInputSchema` in `createWorkoutAction`, like any manual entry.

The user's text is wrapped in `<workout>` tags and the prompt treats it as data. A successful prompt injection can at worst produce an odd draft the user sees before saving: the model has no tools and no database access.

**Why:** A strict schema in layer 1 would make the SDK throw away the whole response over one bad value (see [lessons.md](lessons.md#15-strict-structured-output-schemas-throw-away-whole-responses)).

## 13. Haiku for parsing, chosen by eval

**Decision:** The parser uses Claude Haiku 5.5 at `low` effort, with a 15-second timeout and one retry. `npm run eval:parser` scores a model against 15 fixed cases.

**Why:** On the eval, Haiku and Opus 5.5 both scored 15/15. Haiku's median latency was 1.4s against 2.1s, at roughly 1/40th of the cost (about $0.0003 per parse). Opus is one argument away if accuracy ever becomes the problem.

**Alternatives:** Opus by default: slower and more expensive with no measured accuracy gain on this task. The model is injected (`WorkoutModel`), so unit tests use canned responses instead of mocking the SDK.

## 14. New exercises are created at save time, in a shared catalog

**Decision:** An exercise entry is either an `exerciseId` or a `newExerciseName`. `createWorkout` resolves new names in the same transaction with `INSERT ... ON CONFLICT DO NOTHING` against the `lower(name)` unique index, so a "new" name that already exists reuses that exercise. The catalog is shared by all users.

**Why:** Parsing shouldn't write data the user may never save. Letting the unique index decide makes find-or-create safe under concurrent saves, unlike a check-then-insert in code.

**Trade-off:** One user's custom exercise appears in everyone's list. For a real product, show seeded exercises plus your own (`created_by IS NULL OR created_by = me`).

## 15. Known gap: no rate limit on parsing

**Decision:** Not addressed yet. Parsing requires a logged-in user and input is capped at 1,000 characters, but a user could still call it repeatedly and run up API costs.

**Why deferred:** An in-memory limiter doesn't work across serverless instances; a real one needs shared storage (a Postgres table or a Redis-backed limiter). The per-parse cost is small (decision 13), so this is a hardening task rather than a blocker.

## 16. Dark-only, with semantic color tokens

**Decision:** The app has one dark theme. Colors are tokens defined once in `globals.css` (`page`, `surface`, `elevated`, `fg`, `muted`, `line`, `accent` `#FF9200`, `focus`, `danger`, `warning`) and exposed to Tailwind with `@theme inline`; components use `bg-surface text-muted border-line`, never palette colors or `dark:`. Bordered surfaces are always opaque so the dot-grid background only shows in margins.

**Why:** One consistent look for demos and screenshots, half the visual states to check, and a single place to change a color. New screens (like the coach view) match by default.

**Alternatives:** Light and dark following the system: more flexible, but screenshots depend on the viewer and every screen needs checking twice. A theme toggle: extra state and a flash-of-wrong-theme problem for no demo benefit.

## 17. The role is chosen at signup

**Decision:** Signup asks "athlete or coach". The role travels in Supabase signup metadata, and the profile trigger stores `coach` only for exactly `'coach'`; anything else becomes `athlete` ([`0003_profile_role.sql`](../drizzle/0003_profile_role.sql)).

**Why it's safe:** Metadata is user-controlled, but the role grants nothing by itself. A coach sees no data until an athlete adds them (18), and the trigger can only ever produce the two defined roles.

**Alternatives:** Everyone starts as an athlete and switches on a settings page: one more screen for the same outcome.

## 18. Athletes grant access; coaches can't request it

**Decision:** An athlete adds a coach by email on the Sharing page and can remove them at any time; that link is the only thing that gives a coach read access. `addCoach` checks both roles in the same transaction, and an unknown email and a non-coach email return the same error.

**Why:** The athlete owns the data, so only they can share it. If coaches could add athletes by email, any coach could read anyone's history by knowing their address. The identical error keeps the form from revealing which emails have accounts.

**Later:** A coach-specific invite link that signs an athlete up already linked. Still athlete-initiated, with less typing.

## 19. Denied access is a 404, not a 403

**Decision:** `listAthleteWorkoutsForCoach` returns `null` both when the athlete isn't linked and when the id doesn't exist, and `/athletes/[id]` turns either into `notFound()`. Malformed ids are rejected by Zod before any query.

**Why:** A 403 would confirm that the id belongs to a real athlete. With one response for both cases, guessing ids reveals nothing.

**Alternatives:** 403 for "exists but not yours": more precise for debugging, but it leaks existence, and there's no legitimate user who needs that distinction.

## 20. Data-access tests run on PGlite

**Decision:** Tests for `src/server/` run against PGlite (Postgres compiled to WebAssembly, in memory, in the Vitest process) with the app's real migrations, plus a small stub of Supabase's `auth.users` and API roles ([`src/test/db.ts`](../src/test/db.ts)). Each test file gets its own database.

**Why:** Real SQL, constraints, and the real profile trigger, with no Docker, network, or secrets, so it runs anywhere including CI. The full suite takes about three seconds.

**Alternatives:** The Supabase database: slow, shared with production data, and needs secrets in CI. Docker Postgres: the most faithful, but heavier to run locally and in CI. Mocking Drizzle: fast, but it wouldn't test the SQL, which is where the access rules live.

**Doesn't cover:** Supabase-only behavior (the REST API, RLS as enforced by its roles, Auth itself). That's acceptable because authorization lives in the data layer (3), which these tests exercise directly, including a manual mutation check of the access rule ([lessons.md](lessons.md#18-denial-tests-can-pass-without-the-rule-theyre-testing)).
